# تدقيق لوحة الإدارة وخطة الذكاء الاصطناعي الآمن — 2026-11-08

**الفرع:** `alwaha-pro-3.0.3-final-rebuild-20261107`
**النطاق:** مراجعة الملفات الحالية في `admin-app` و`supabase/functions/admin-api`، ووضع متطلبات إكمال الإدارة ودعم الذكاء الاصطناعي.
**القرار:** لا نعتبر لوحة الإدارة الحالية مكتباً إدارياً كاملاً، ولا ننشئ جداول دعم أو نضيف أسرار مزود AI قبل تثبيت متطلبات الخصوصية والصلاحيات.

## 1) الجرد الفعلي لما يعمل في المصدر

لوحة `pro.alwaha.admin` الحالية منفصلة عن التطبيق الأساسي، وتستخدم `admin-api` عبر `supabase.functions.invoke`. الدالة المنشورة التي تمت مطابقة مصدرها سابقاً تتحقق من JWT عبر `auth.getUser` ثم تستعلم عن `users.is_admin` من الخادم، وتكتب سجلاً لكل طلب إداري قبل تنفيذ الإجراء.

الإجراءات الخمسة الموجودة فعلياً في API:
- `summary`: عدد الحسابات وإجمالي طلبات التوثيق المعلقة.
- `list_users`: عرض وبحث الحسابات مع حقول محددة.
- `list_verification_requests`: قائمة طلبات التوثيق وحالاتها.
- `review_verification`: قبول أو رفض طلب توثيق ما زال معلقاً.
- `list_audit_logs`: عرض سجل الإجراءات الإدارية.

الواجهة الحالية تعرض ثلاث شاشات: طلبات التوثيق، الحسابات، وسجل التدقيق. لا تقرأ جداول المستخدمين مباشرة من المتصفح ولا تحتوي مفتاح `service_role`. هذه نقطة جيدة يجب الحفاظ عليها.

## 2) ما ينقص اللوحة الحالية

| المجال | الحالة الحالية | ما نحتاجه قبل/بعد الإطلاق |
|---|---|---|
| الحسابات | عرض وبحث فقط | تعطيل/تقييد/استعادة الحساب ضمن صلاحيات محددة، مع سبب ومدة وسجل تدقيق |
| التوثيق | مراجعة قبول/رفض | تفاصيل مراجعة آمنة، سبب القرار، إعادة فتح/استئناف، وعدم كشف بيانات غير لازمة |
| البلاغات | غير موجود | قائمة بلاغات، أولوية وحالة وتعيين لمراجع، سجل قرارات |
| المحتوى والمنشورات | غير موجود | مراجعة بلاغات، إخفاء مؤقت/استعادة، سجل أدلة وسبب القرار |
| الريلز والتعليقات | غير موجود | طابور مراجعة منفصل وإجراءات متدرجة |
| السوق | غير موجود | بلاغات البائع/المشتري، المنتجات، النزاعات، سجلات المعاملات؛ لا صلاحيات حذف تعسفي |
| الألعاب والغرف | غير موجود | بلاغات الغرف، إساءة الاستخدام، ومراقبة سلامة الخدمة دون التلاعب بنتائج اللعب |
| الأدوار | `is_admin` عام | أدوار محددة مثل دعم/مراجعة/مشرف/مسؤول، بأقل صلاحية لازمة |
| التشغيل والمراقبة | لا توجد شاشة تشغيل | صحة Edge Functions وRealtime وPostgres، معدلات الأخطاء، زمن الاستجابة، تنبيهات |
| الإعدادات | غير موجود | Feature flags وإعدادات عامة مع مراجعة، سجل تغييرات، وإمكانية رجوع |
| خدمة العملاء | غير موجودة | تذاكر، ردود بشرية، تحويل للمسؤول، مساعد RAG مضبوط |
| تقارير الأداء والأمان | غير موجودة | تقارير مجمعة لا تكشف نصوص الرسائل أو الرموز أو أسرار المستخدمين |
| إدارة الإصدارات | غير موجودة | عرض آخر CI والبناء والتوقيع والنسخة المنشورة؛ لا نشر تلقائي من شاشة الإدارة |

لا نضيف إجراءً إدارياً لمجرد توفر زر. كل إجراء يجب أن يملك: صلاحية خادمية، تحققاً من حالة الهدف، سبباً إلزامياً عند الحاجة، تسجيل تدقيق قبل/بعد، واختباراً يثبت رفض غير المصرح له.

## 3) نموذج الصلاحيات المقترح

لا نكتفي بتوسيع `is_admin` إلى كل الموظفين. نحتفظ بحساب مسؤول أساسي، ونضيف نظاماً خادمياً للأدوار والنطاقات، مثلاً:
- `support_agent`: الاطلاع على تذاكر الدعم والرد عليها فقط.
- `content_moderator`: مراجعة البلاغات والمحتوى ضمن نطاق محدد.
- `marketplace_moderator`: مراجعة المنتجات والنزاعات دون تعديل المدفوعات.
- `trust_safety`: مراجعة إساءة الاستخدام والحالات الحساسة.
- `operations_viewer`: مراقبة الصحة والأداء دون إجراءات تعديل.
- `super_admin`: إدارة الأدوار والإعدادات الحساسة بعد مصادقة أقوى.

تُفحص الصلاحية والنطاق داخل Edge Function في كل طلب، وليس من إخفاء الأزرار في المتصفح. التغييرات الحساسة تحتاج MFA/إعادة تحقق وتأكيداً بشرياً، وتُسجل في جدول التدقيق. لا نعرض كلمات المرور أو مفاتيح الجلسات أو مفاتيح API للمدير.

## 4) بنية مساعد الدعم الذكي بطريقة آمنة

المسار المعتمد:

`Alwaha app -> authenticated Supabase Edge Function -> scoped RAG retrieval -> AI provider -> validated response -> app`

- مفتاح المزود يكون في أسرار Edge Function فقط، ولا يدخل HTML أو JavaScript أو APK أو GitHub artifacts أو سجلات العميل.
- تستقبل الدالة JWT وتتحقق من المستخدم عبر `auth.getUser`، ثم تفرض حدوداً لحجم الرسالة ومعدل الطلب والميزانية.
- يبدأ RAG من مصادر منشورة ومراجعة: دليل التطبيق، الأسئلة الشائعة، سياسات السوق، خطوات الاستخدام، وسياسات الخصوصية. لا نسمح للنموذج باستعلام جداول المستخدمين أو الرسائل الخاصة أو الدفع.
- لا نمرر بيانات الحساب إلا عند ضرورة دعم محددة وبأقل قدر ممكن. نزيل الرموز والبريد والهاتف والمعرفات من سجلات الأخطاء.
- لا نعطي مساعد المستخدم أدوات إدارية أو SQL أو تنفيذ أوامر. يجيب ويشرح، وعند عدم المعرفة يحول المستخدم إلى دعم بشري.
- نتحقق من سياسة الاحتفاظ لدى مزود النموذج وخيارات عدم التدريب قبل التفعيل؛ لا نعد المستخدم بسرية مطلقة لا يمكن إثباتها.
- نفصل مساعد دعم المستخدمين عن مساعد الإدارة. مساعد الإدارة يبدأ بقراءات مجمعة ومقاييس تشغيل منزوعة الهوية؛ لا يحصل تلقائياً على محتوى المحادثات أو صلاحية تنفيذ إجراءات.

## 5) مخطط قاعدة بيانات دعم مقترح — ليس ترحيلاً مطبقاً

نفضّل فصل المحادثة عن الرسائل بدلاً من حقل JSON واحد كبير:

- `support_conversations`: `id`, `user_id`, `status`, `consent_at`, `created_at`, `updated_at`, `closed_at`.
- `support_messages`: `id`, `conversation_id`, `sender_role`, `body`, `created_at`, `safety_state`, `provider_metadata` محدود وخالٍ من الأسرار.
- `support_knowledge`: وثائق مساعدة منشورة فقط مع اللغة والتصنيف ومصدر المراجعة ونسخة المحتوى وembedding.

قواعد مطلوبة:
1. `support_conversations.user_id` مرتبط بـ `auth.users` ولا يقبل العميل تعيين مستخدم آخر.
2. RLS يسمح للمستخدم بقراءة محادثاته فقط، ولا يسمح له بإنشاء رسائل باسم `assistant` أو `agent`.
3. إدخال رد المساعد يتم من Edge Function بعد التحقق من مالك المحادثة؛ لا توجد صلاحية service key في التطبيق.
4. الوصول الإداري إلى تذكرة دعم يتم عبر إجراء خادمي منفصل ومقيد بالدور، ويسجل كل فتح/قراءة/رد إداري.
5. لا نحتفظ بالمحادثات للأبد افتراضياً. نحدد مدة الاحتفاظ والغرض والموافقة والحذف والتصدير قبل الإطلاق.
6. بيانات RAG لا تشمل رسائل الناس الخاصة، ولا تصبح قاعدة المعرفة قابلة للكتابة من حسابات المستخدمين.

هذا القسم مواصفة تصميم فقط. لم تُنشأ الجداول أو migrations أو Edge Function للدعم بعد.

## 6) مراقبة الأخطاء والذكاء الاصطناعي في دورة التطوير

- يمكن دمج Sentry أو منصة مماثلة بعد ضبط إزالة PII والتوكنات ومحتوى الرسائل، وتقييد الوصول إلى source maps والسجلات.
- سجلات Supabase تستخدم لمؤشرات الخدمة والأخطاء، لا لنسخ محتوى المستخدمين إلى النموذج.
- GitHub Actions ينفذ الاختبارات والتحليل الأمني والبناء؛ مساعد AI يقترح patch أو Pull Request فقط. لا يسمح للنموذج بدمج نفسه أو نشر كود/قاعدة إنتاج مباشرة.
- يجب أن تكون نتائج التحليل قابلة للمراجعة: المرجع، commit، الملف والسطر، الاختبار الذي أثبت المشكلة، والتغيير المقترح.

## 7) مراحل التنفيذ والأولوية

**أ — قبل الإصدار العام:** إكمال بوابات سلامة التطبيق الحالية، صلاحيات قاعدة البيانات، إدارة جلسات المدير، اختبار OTP/تسجيل الدخول الحقيقي، ثبات اللوحة الأساسية، سجل التدقيق، وبناء APK/AAB موثق. لا نربط AI ببيانات الإنتاج خلال هذه المرحلة.

**ب — مركز الإدارة:** إضافة الأدوار والنطاقات، طوابير البلاغات، مراجعة المحتوى والسوق، إجراءات التقييد/الاستعادة، تذاكر الدعم، وسجل مراجعة موحد. كل وظيفة خلف صلاحية واختبار.

**ج — التشغيل والمراقبة:** مؤشرات صحة الخدمات والأخطاء والأداء، تنبيه الحوادث، مؤشرات النسخ الاحتياطي والإصدارات، وإعدادات الميزات ذات سجل تغيير ورجوع.

**د — مساعد الدعم RAG:** نشر مصدر معرفة عام ومراجع، Edge Function منفصلة، حماية إساءة الاستخدام، سياسة الاحتفاظ والموافقة، اختبار تسريب بين المستخدمين، واختبار prompt injection قبل تفعيلها تدريجياً.

**هـ — مساعد الإدارة:** تقارير مجمعة ومقترحات فقط أولاً؛ كل تعديل إداري يحتاج قراراً بشرياً وتحققاً خادمياً. لا وصول شامل إلى بيانات الرسائل الخاصة.

## 8) بوابات القبول

- اختبار RLS بين حسابين: لا يرى أحد محادثة أو تذكرة أو رسالة الآخر.
- اختبار رفض العميل كتابة رسالة مساعد أو التظاهر بدور مدير.
- اختبار مفاتيح: لا مفتاح AI أو service-role في bundle أو APK أو Git أو logs.
- اختبار rate limit وحجم المدخلات والميزانية والتعامل مع انقطاع المزود.
- اختبار prompt injection في نص المستخدم وفي الوثائق المسترجعة.
- اختبار الحذف والاحتفاظ والموافقة والتصدير.
- تدقيق سجل الإدارة: من فعل ماذا، ومتى، وعلى أي هدف، والنتيجة، دون تخزين أسرار.
- عدم تفعيل AI للمستخدمين قبل نجاح الاختبارات ومراجعة إعدادات خصوصية المزود.

## 9) ملاحظات تنفيذية إضافية

- واجهة الإدارة الحالية تعتمد على CDN خارجي لتحميل Supabase JS؛ ينبغي تثبيت نسخة محددة محلياً أو تأمينها ببصمة SRI وسياسة CSP مناسبة قبل الاعتماد التشغيلي، لتقليل الاعتماد على مصدر خارجي وقت التشغيل.
- يجب إضافة MFA للحسابات الإدارية، وجلسات قصيرة/إعادة تحقق للإجراءات الحساسة.
- لا يُنشأ جدول `support_chats` وحده قبل تحديد هيكل المحادثة والرسائل وسياسة الاحتفاظ؛ فصل الجدولين أعلاه يمنع تداخل صلاحيات القراءة والكتابة ويتيح المراجعة والحذف.
- هذا المستند لا يفعّل أي وظيفة في قاعدة الإنتاج ولا يغيّر صلاحيات المستخدمين.
