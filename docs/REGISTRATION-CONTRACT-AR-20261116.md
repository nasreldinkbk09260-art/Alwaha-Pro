# عقد إنشاء الحساب — Alwaha-Pro 3.0.3

**تاريخ الاعتماد:** 16 نوفمبر 2026  
**الحالة:** متطلب منتج ثابت؛ لا يُغيّر إلا بقرار صريح موثق من مالك المشروع.

## الحقول الأساسية المطلوبة
1. الاسم الظاهر للمستخدم.
2. اسم المستخدم الفريد (3–32 حرفًا إنجليزيًا صغيرًا أو رقمًا أو شرطة سفلية). يُقترح تلقائيًا ويستطيع المستخدم تعديله.
3. كلمة مرور من 8 إلى 128 حرفًا.
4. حقل منفصل لتأكيد كلمة المرور، ويجب أن يطابقها.
5. زر مستقل لإظهار/إخفاء كلمة المرور وزر مماثل لحقل التأكيد.

## حقول اختيارية
**البريد الإلكتروني والهاتف اختياريان** ويمكن تركهما فارغين تمامًا عند إنشاء الحساب.
- البريد الإلكتروني: اختياري. عند تقديمه يستخدم مسار تأكيد البريد الحقيقي في Supabase Auth؛ لا يُسمح بتسجيل الدخول قبل تنفيذ التأكيد وفق إعدادات Auth.
- الهاتف: اختياري، ولا يُستخدم كهوية دخول أو وسيلة استعادة ما لم يُفعّل مسار تحقق مستقل.
- الصورة الشخصية: اختيارية وتظهر أعلى نموذج التسجيل.
- الاسم الأخير والجنس وتاريخ الميلاد: بيانات إضافية اختيارية.

## ترتيب الواجهة وإكمال الملف بعد التسجيل
- ترتيب النموذج: الصورة الشخصية الاختيارية أولًا، ثم الاسم الظاهر، ثم اسم المستخدم المقترح تلقائيًا والقابل للتعديل، ثم كلمة المرور وتأكيدها.
- البريد والهاتف وبقية التفاصيل الاختيارية داخل قسم إضافي قابل للفتح، ولا تعيق إنشاء الحساب عند تركها فارغة.
- بعد إنشاء الحساب يظهر زر «تعديل بياناتي» للمستخدم المسجل، ويمكنه إضافة أو تعديل الاسم واسم المستخدم والبريد والهاتف والصورة والجنس وتاريخ الميلاد.
- تغيير البريد يمر بمسار تأكيد Auth؛ لا يُعامل البريد الجديد على أنه موثّق قبل تأكيده.
- تحديث بيانات الملف يتم عبر Edge Function موثقة بـJWT وقائمة حقول مسموحة، ولا يحصل العميل على صلاحية UPDATE عامة لجدول users.

## تغيير كلمة المرور من داخل الحساب

- يوفّر التطبيق خيارًا منفصلًا لتغيير كلمة المرور بعد إدخال كلمة المرور الحالية والتحقق منها عبر مسار Auth المناسب للحساب.
- يعيد المسار تثبيت جلسة تخص معرّف الحساب نفسه قبل حفظ كلمة المرور الجديدة، ويرفض أي اختلاف في هوية الجلسة.
- لا يحل هذا الخيار محل استعادة الحساب عند نسيان كلمة المرور الحالية؛ الحساب الذي لا يملك بريدًا موثّقًا قد يفقد الوصول إذا نسي كلمة المرور قبل تغييرها.

## حساب بدون بريد أو هاتف
Supabase Password Auth يربط كلمة المرور بهوية بريد أو هاتف؛ لذلك ينشئ الخادم هوية Auth داخلية عشوائية على النطاق المحجوز غير القابل للتسليم `.invalid` عند غياب البريد، ويؤكدها داخليًا، ثم يسجل دخول المستخدم عبر اسم المستخدم إلى الهوية الداخلية. لا تظهر هذه الهوية للمستخدم ولا تُستخدم كبريد تواصل.
لا يُسمح بوضع Service Role أو المفتاح السري في المتصفح؛ إنشاء هذه الهوية يتم داخل Edge Function فقط.

## الاستعادة والخصوصية
- الحساب الذي لا يربط بريدًا حقيقيًا موثقًا لا يستطيع استعادة كلمة المرور عبر البريد. يجب تنبيه المستخدم إلى حفظ كلمة المرور؛ فقدانها قد يعني فقدان الوصول.
- البريد الذي يقدمه المستخدم لا يُعد موثقًا لمجرد إدخاله.
- الهاتف والبريد لا يظهران في الدليل العام، وتظل إعدادات إخفاء بيانات الاتصال مفعلة.
- الموافقة على إصداري الشروط والخصوصية الحاليين شرط إنشاء الحساب.
- لا يُنشأ مستخدم تجريبي في قاعدة الإنتاج بغرض الاختبار.

## بوابة عدم التراجع
أي تغيير لاحق يجعل البريد أو الهاتف إلزاميًا، يخفي تأكيد كلمة المرور، يزيل زر إظهار كلمة المرور، أو يلغي اسم المستخدم التلقائي القابل للتعديل، يُعد كسرًا لهذا العقد ويجب أن يفشل اختبار قبول التسجيل حتى يصدر قرار تغيير صريح ونسخة جديدة من هذا المستند.
