## 4. حدود لم تكتمل بعد — لا تُعرض على أنها منجزة

### أ. المكالمات الجماعية / إضافة مشارك
محرك `CallSignalingManager` الحالي يدير جلسة مع طرف واحد، ويشترط رفض الطلب الجديد إذا كانت هناك مكالمة أو دعوة قائمة. لا توجد بعد إدارة غرفة متعددة الأعضاء أو عدة PeerConnections ومسارات صوت/فيديو منفصلة وصلاحيات وطرد/مغادرة وإنهاء متسق. لذلك لم يُعرض زر إضافة مشارك شكلياً. هذه ميزة مستقلة تحتاج تصميم وتنفيذ واختبارات متعددة الأطراف.

### ب. شبكة Mesh متعددة الجيران
إضافة Android تحتفظ حالياً بمقبس TCP نشط واحد ومقبس RFCOMM نشط واحد لكل نسخة اتصال، ويستبدل الاتصال الجديد المقبس القديم في المسار نفسه. طبقة JavaScript تتعامل مع جار نقل نشط واحد في الوقت الحالي. طابور relay مشفر ومختبر منطقياً، لكن هذا لا يساوي عدة جيران متزامنين أو اختيار المسار أو توجيهاً متعدد المسارات مجرباً على أجهزة.

### ج. مكالمات Mesh
Bluetooth Classic ينقل رسائل وملفات مشفرة ولا ينقل WebRTC الحي. مكالمة محلية مباشرة تتطلب Wi‑Fi Direct واتصالاً مباشراً بالجار الموثق. لا يوجد تمرير WebRTC للصوت والفيديو عبر عدة قفزات.

### د. العمل دون اتصال
التطبيق يعرض بيانات سابقة مخزنة ومشفرة فقط؛ لا يمكن إظهار محتوى لم يُحمّل قبل فصل الإنترنت. بعض الإجراءات للقراءة فقط أو تتطلب الاتصال. المزامنة ليست تسوية تعارض عامة لكل أقسام التطبيق، ولا يجب السماح بإعادة تشغيل عمليات بيع أو رسائل مكررة عند الرجوع للشبكة.

### هـ. الاختبار الميداني
لا يثبت CI صحة راديو Bluetooth/Wi‑Fi Direct على هواتف حقيقية ولا جودة الكاميرا والميكروفون والصوت والبطارية والخلفية. لم يتم اختبار هاتفين فعليين في هذه المراجعة. كما أن Chrome mobile emulation ليس Android WebView.
