## نتائج أولية مهمة
1. الصفحة الرئيسية `index.html` ما زالت نقطة تجميع كبيرة وتحتوي أنماطاً ومعالجات مضمنة؛ لا نضيف معالجات جديدة فيها قبل فحص مالك الإجراء الحالي.
2. بعض عناصر الملف الشخصي تُنشأ ديناميكياً؛ لذلك فحص HTML الخام وحده لا يكشف جميع الأزرار ولا التكرار الذي يظهر بعد فتح القوائم.
3. فحص `ui-handler-audit` الحالي يتحقق أساساً من وجود تعريفات لمعالجات الأحداث، ولا يثبت أن لكل إجراء زرّاً واحداً فقط.
4. فحص التكرار الحالي في `field-repair-audit` يغطي المعرفات الثابتة داخل `index.html` فقط؛ ولا يغطي أسماء مختلفة لنفس الوظيفة أو العناصر المضافة وقت التشغيل.
5. اختبار العرض البصري الحالي يعمل في متصفح آلي وبخدمات خلفية محجوبة/محاكاة في بعض السيناريوهات؛ لا يثبت نجاح الحسابات الفعلية أو المكالمات أو أجهزة الراديو.
6. توجد طبقات متداخلة: معالجات مضمنة في الصفحة، وحدات مستقلة، وطبقة توافق، وإضافات DOM وقت التشغيل. يجب توحيد ملكية الإجراء قبل حذف أي زر.

## ترتيب الفحص التالي
- استخراج كل عناصر التفاعل الثابتة من HTML مع: المعرّف، القسم، النص، aria-label، title، onclick، data-action، نوع العنصر، وحالة الإخفاء.
- فتح/تشغيل كل وحدة تضيف عناصر وقت التشغيل واستخراج العناصر الديناميكية بعد التهيئة.
- بناء سجل إجراءات canonical: إجراء واحد = action key واحد = handler واحد = مالك واحد.
- مقارنة الأزرار داخل نطاق الشاشة/القسم نفسه، وليس على مستوى التطبيق كله؛ فقد تتكرر وظيفة الرجوع أو الحفظ في نوافذ مستقلة بشكل مشروع.
- اكتشاف aliases: دوال بأسماء مختلفة تنتهي إلى نفس الإجراء أو تستدعي نفس العملية الأساسية.
- إخراج تقرير يفرّق بين duplicate مؤكد، alias محتمل، وتكرار مشروع؛ لا حذف آلياً قبل مراجعة السياق.
- بعد اعتماد السجل، إزالة الزائد وإضافة اختبار يمنع عودة التكرار.
