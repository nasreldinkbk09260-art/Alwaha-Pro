**نطاق العمل:** قراءة مباشرة للمشروع، سجل الترحيلات، Edge Functions، Supabase Advisors، واستعلامات SQL من نوع SELECT فقط.  
**التغيير الإنتاجي في هذه المراجعة:** لا شيء. لم ينفذ أي DDL أو DML أو نشر Edge Function أو تغيير إعداد Auth.

## 3. حالة مخطط الإنتاج والاحتفاظ

أثبتت استعلامات القراءة وجود الجداول والوظائف التالية:
- `market_transactions` و`market_conversations` و`reel_views` و`game_rooms`.
- حقول لقطة الإعلان، تاريخ الاحتفاظ، تاريخ إرسال الإشعار، وموافقتَي المشتري والبائع موجودة في سجل السوق والمعاملات.
- دالتا `request_market_delivery` و`update_market_delivery` موجودتان.
- دالة `purge_expired_marketplace_archives(integer)` موجودة.

### مهمة الاحتفاظ

- امتداد `pg_cron` مثبت.
- المهمة `alwaha-marketplace-retention-daily` موجودة ونشطة.
- الجدول: `0 3 * * *` (03:00 UTC يوميًا).
- أمر المهمة يستدعي دالة تنظيف الأرشيف المتوقعة.
- جسم الدالة الحية يرسل إشعارًا للطرفين قبل الحذف، وينتظر 7 أيام كاملة بعد الإشعار، ويفحص `retention_until` وموافقتَي المشتري والبائع، ويستثني المعاملات المتنازع عليها أو التي لا تزال ضمن فترة الاحتفاظ.
- دالة التنظيف `SECURITY DEFINER` مملوكة لـ`postgres` مع `search_path` فارغ، لكن صلاحية EXECUTE ممنوعة عن `anon` و`authenticated` وممنوحة لـ`service_role` فقط؛ وهذا يقصر استدعاءها المباشر على المسار الخلفي/المهمة.

لم تُنفذ عملية تنظيف أو حذف يدوي. وجود المهمة النشطة لا يبرر إجراء حذف اختباري على سجلات جمهور التطبيق.

## 4. صلاحيات معاملات السوق

أثبت الاستعلام الحي ما يلي:
- سياستا UPDATE موجودتان: `market_transactions_buyer_confirm_receipt` و`market_transactions_seller_delivery_update`.
- شرط كل سياسة يقصر الصفوف على `buyer_id = auth.uid()` أو `seller_id = auth.uid()` على الترتيب، مع شرط `WITH CHECK` المقابل.
- دور `authenticated` لا يملك UPDATE عامًا على الجدول كله.
- صلاحيات تحديث الأعمدة المحددة فقط (ومنها `buyer_confirmed_at` وحقول التسليم) موجودة.
- مشغل الحماية موجود، ويعمل `SECURITY INVOKER` مع `search_path` فارغًا.

لذلك يظهر تحذير `multiple_permissive_policies` بوصفه ملاحظة أداء لوجود سياستين UPDATE، لا دليلاً بذاته على أن البائع يستطيع تحديث صف مشتري أو العكس. لا تدمج السياستين ولا توسع الصلاحيات لإزالة التحذير دون اختبار SQL يثبت التكافؤ الكامل بين شروط السياسات والمشغل وصلاحيات الأعمدة.

## 5. جداول RLS بلا سياسات

أظهر Security Advisor ستة جداول ذات RLS مفعّل ودون سياسات:
- `admin_action_logs`
- `app_settings`
- `content_reports`
- `support_tickets`
- `user_blocks`
- `user_consents`

تم التحقق من الامتيازات مباشرة: لا يملك `anon` أو `authenticated` صلاحيات SELECT/INSERT/UPDATE/DELETE المباشرة على هذه الجداول؛ `service_role` و`postgres` لديهما الامتيازات الخلفية المتوقعة.

**القرار:** أبقِ هذه الجداول على `default-deny`. التنبيه معلوماتي في هذا التصميم، وإضافة سياسة عامة أو صلاحية مباشرة لإزالة التنبيه ستكون إضعافًا غير مبرر للحماية.

## 6. نتائج Supabase Advisors الحية

### الأمن

- `auth_leaked_password_protection` — WARN واحد: حماية كلمات المرور المسرّبة غير مفعّلة.
- `rls_enabled_no_policy` — INFO لستة جداول. تم التحقق في القسم السابق من عدم وجود صلاحيات مباشرة لأدوار العميل.

### الأداء

- `unindexed_foreign_keys` — INFO: المفتاح الأجنبي `reel_views_user_id_fkey` لا يملك فهرسًا يغطي `user_id`. الفهرس الفريد الحالي يبدأ بـ`reel_id` ثم `user_id`، ولذلك لم يعتبره Advisor تغطية كافية لمفتاح `user_id`.
- `multiple_permissive_policies` — WARN واحد على سياستي UPDATE في `market_transactions` للمشتري والبائع. انظر القسم 4.
- `unused_index` — INFO لـ25 فهرسًا لم تستخدمها إحصاءات القاعدة بعد.

**لا تحذف الفهارس غير المستخدمة اعتمادًا على هذه اللقطة وحدها**؛ قد تكون قاعدة البيانات قليلة الاستخدام، وقد تخدم الفهارس مسارات موسمّية أو حذفًا مرجعيًا أو تقارير لم تُنفذ بعد.

## 7. سبب بقاء حماية كلمات المرور المسرّبة

تقرير المؤسسة الحي يعرض الخطة `Free`. توثيق Supabase الرسمي يذكر أن ميزة Leaked Password Protection المدمجة في Auth متاحة على Pro وما فوق، وتوجد في إعدادات Auth الخاصة بمزوّد Email:

https://supabase.com/docs/guides/auth/password-security

المسار الحالي في لوحة التحكم بعد توفر الخطة والصلاحية:
`Authentication → Sign In / Providers → Email`، ثم تفعيل منع كلمات المرور المسرّبة وحفظ الإعداد.

أدوات Supabase المتاحة في هذه الجلسة تعرض Advisors وSQL والوظائف، لكنها لا تعرض إجراء كتابة إعداد Auth هذا. لذلك لم نحاول محاكاة الإعداد بترحيل SQL أو تعديل RLS.

**الحالة:** بوابة إعداد لدى مالك المشروع/الخطة؛ ليست مشكلة يمكن حلها بتعديل جدول. لا تعتبرها مفعّلة حتى يُعاد تشغيل Security Advisor ويختفي التحذير. لا نطلب ترقية مدفوعة تلقائيًا ولا نتخذ قرار تكلفة نيابة عن المالك.

## 9. ميزات ما زالت خارج إثبات Beta 1387

هذه حدود مصدر/تشغيل أو اختبار، وليست دعوة لتغيير ما اجتاز CI دون سبب:
- لا يوجد مستمع Push في `sw.js`، ولا تكامل Firebase Messaging/Capacitor Push Notifications ضمن المصدر الذي تمت مراجعته؛ لذلك لا تُعلن إشعارات النظام بعد إنهاء التطبيق مكتملة.
- محرك المكالمة الحالي يوجّه جلسة إلى طرف `peerId` واحد؛ لا توجد بنية غرفة متعددة الأعضاء/مؤتمرات مثبتة. لا تُعلن المكالمات الجماعية.
- إضافة Android المحلية تعيد `callMediaReady=false` لمسار الجسر/الترحيل. الرسائل والملفات المشفرة عبر الجسر منفصلة عن وسائط WebRTC الحية؛ لا تُعلن المكالمات عبر وسيط Mesh مكتملة.
- يوجد مسار اتصال محلي مباشر مشروط بنوع نقل `wifi-direct-tcp` والطرف الموثق؛ لا يُعلن نجاحه حتى اختبار جهازين.
- القيمة الافتراضية في مصدر `admin-api` تعرض وسائل تحويل يدوية (InstaPay وVodafone Cash وتحويل بنكي)، وتضع خطتي Plus/Premium وطرق الدفع الافتراضية على `enabled=false`. لم أقرأ أو أعرض أي مراجع حسابات مخزنة للمؤسسة. لم يظهر تكامل مزود دفع آلي أو Checkout/Webhook في الملفات التي تمت مراجعتها؛ لا تُعلن الاشتراكات الآلية جاهزة.
- اختبار غرفة الأطفال والفلاتر والصوت والألعاب يحتاج مكالمة فيديو فعلية على جهازين ووصول إطار فيديو حقيقي.

## 10. التحذيرات التي لا يجوز إصلاحها عشوائيًا

1. لا تنشئ سياسات على الجداول الستة لمجرد إزالة INFO.
2. لا توسّع UPDATE على `market_transactions` ولا تدمج سياسات المشتري والبائع دون اختبار equivalence.
3. لا تحذف 25 فهرسًا غير مستخدم اعتمادًا على Advisor وحده.
4. لا تضف فهرس `reel_views(user_id)` إلى الإنتاج مباشرة. إن اعتمد لاحقًا، أنشئ migration جديدة عبر Supabase CLI، واختبرها في PostgreSQL منفصل، ثم أعد فحص Advisor.
5. لا تغيّر إعداد Auth أو الخطة أو تنشر Edge Functions دون موافقة صريحة وتحقق لاحق.

## 11. الخلاصة وحالة التنفيذ

**نجح الفحص الحي:** المشروع سليم، والوظائف الثماني تطابق المصدر، وميزات السوق/التوصيل/الاحتفاظ التي استُعلم عنها موجودة، ومهمة الاحتفاظ النشطة تشترط موافقة الطرفين، والجداول الستة المقفلة ليست مكشوفة لأدوار العميل.

**ما بقي:** بوابة Auth المدمجة (مرتبطة بخطة Pro)، ملاحظات أداء غير حرجة، واختبارات الهاتفين الميدانية F01–F22. كما تبقى Push/FCM والمكالمات الجماعية ووسائط Mesh عبر وسيط ودفع الاشتراكات الآلي غير مثبتة/غير موجودة كتكامل مكتمل في المصدر الحالي.

**لا تغييرات إنتاجية في هذه المراجعة.** هذا الملف سجل قراءة وتوثيق فقط، وأضيف إلى فرع `work` دون تعديل كود التطبيق أو الاختبارات أو SQL.
